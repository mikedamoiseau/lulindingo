# Daily Quest Board Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a small **Daily Quest Board** to the home screen showing three quests generated deterministically from today's local date. Kids see clear daily goals ("Answer 10 multiplication questions", "Finish a lesson with 3 stars", "Get 5 in a row correct"); progress fills as they play; completing all three awards a bonus reward. Quests reset at local midnight. This deepens the daily-habit loop that the streak already started, giving kids a concrete reason to open the app every day and giving parents a visible "did something today" signal.

**Architecture:** A pure `dailyQuests.js` util derives a deterministic seed from the `getLocalDateString()` string (no `Math.random`, no `Date.now`), picks three quests from a fixed catalog, and evaluates progress against a plain stats object. A new Dexie table `dailyQuests` (keyed by date string) stores today's chosen quest IDs, accumulated counters, and a `claimed` flag. The game store gains a `questStats` slice plus actions that the lesson loop already-present calls (`recordAnswer`, `completeLesson`) feed, so the lesson code barely changes. A `QuestBoard` component on the home screen reads the row via `useLiveQuery`, renders progress, and offers a one-tap claim when all three are done.

**Tech Stack:** React 19, Zustand, Dexie/IndexedDB, Vitest. Offline-first, no backend.

## Key Design Decisions

Concrete, opinionated calls. Each ends with a one-line "why".

### 1. Deterministic seed from the date string (no nondeterminism)

`getLocalDateString()` returns `"YYYY-MM-DD"`. We turn that into a 32-bit integer seed with a small string hash (FNV-1a style), then drive a tiny pure PRNG (mulberry32) off that seed. **No `Math.random`, no `Date.now`, no `new Date()` inside the pure util** — the only time input is the date string passed in by the caller.

```js
export function dateSeed(dateString) {       // "2026-06-22" → uint32
  let h = 0x811c9dc5;
  for (let i = 0; i < dateString.length; i++) {
    h ^= dateString.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  return h >>> 0;
}
function mulberry32(seed) { /* returns () => float in [0,1) */ }
```

**Why:** Same date → same three quests on every device and every reload, with zero persisted "which quests" decision needed beyond caching; trivially unit-testable because it is a pure `(string) → quest[]`.

### 2. Quest catalog & objective types

A frozen `QUEST_CATALOG` array. Each entry: `{ id, type, label(target), target, metric, icon }`. Three **metric** families, each measurable from data we already record:

| metric | meaning | source |
|---|---|---|
| `answerCount` | answered N questions (optionally per-operation) | `recordAnswer` accumulator |
| `lessonStars` | finished a lesson with ≥ N stars today | `completeLesson` accumulator (best stars today) |
| `streakInSession` | got N correct in a row | `recordAnswer` run-length tracker |

Catalog (v1, 8 entries so the daily pick has variety):

```js
export const QUEST_CATALOG = [
  { id: 'answer-10-any',   type: 'answers',  metric: 'answerCount',     target: 10, operation: null,             icon: '✏️' },
  { id: 'answer-15-any',   type: 'answers',  metric: 'answerCount',     target: 15, operation: null,             icon: '✏️' },
  { id: 'answer-10-mul',   type: 'answers',  metric: 'answerCount',     target: 10, operation: 'multiplication', icon: '✖️' },
  { id: 'answer-10-add',   type: 'answers',  metric: 'answerCount',     target: 10, operation: 'addition',       icon: '➕' },
  { id: 'streak-5',        type: 'streak',   metric: 'streakInSession', target: 5,  operation: null,             icon: '🔥' },
  { id: 'streak-8',        type: 'streak',   metric: 'streakInSession', target: 8,  operation: null,             icon: '🔥' },
  { id: 'stars-3',         type: 'stars',    metric: 'lessonStars',     target: 3,  operation: null,             icon: '⭐' },
  { id: 'finish-1-lesson', type: 'lessons',  metric: 'lessonCount',     target: 1,  operation: null,             icon: '🏁' },
];
```

`lessonCount` is a fourth, simple metric (number of non-practice lessons completed today). Labels are generated by a `questLabel(quest)` helper so copy stays in one place and stays kid-readable.

**Why:** Every metric maps onto a counter the lesson loop already produces; no new instrumentation in exercise components; per-operation quests reuse the operation already on each generated exercise/lesson.

### 3. Deterministic selection: pick 3, force variety, respect the child's band

`selectDailyQuests(dateString, ageBand)`:

1. Filter the catalog to quests **achievable for the band**. Operation-specific quests are dropped if the band never sees that operation (band `11-12` skips addition+subtraction per `skipUnits.js`, so `answer-10-add` is filtered out for them).
2. Shuffle the filtered list with the seeded PRNG (Fisher–Yates using `mulberry32(dateSeed(dateString))`).
3. Walk the shuffled list and greedily pick the first three **distinct `type`s** where possible (one "answers", one "streak"/"stars", one "lessons") so a kid never gets three near-identical quests; fall back to filling remaining slots from whatever is left if a type is exhausted.

Returns an array of three catalog entries (full objects, not just IDs). The persisted row stores only the three `id`s plus the date.

**Why:** Deterministic + varied + always achievable; the type-diversity rule is the one piece of "taste" that keeps the board from feeling repetitive, and it is pure so it is fully testable.

### 4. How progress is measured against live events

Two complementary layers, kept decoupled:

- **Source of truth for the day = a `questStats` object** persisted on the `dailyQuests` row:
  ```js
  {
    date, questIds: [a,b,c], claimed: false,
    answerCount: 0,
    answerByOperation: { addition: 0, subtraction: 0, multiplication: 0, division: 0 },
    bestStreakInSession: 0,
    lessonCount: 0,
    bestLessonStars: 0,
  }
  ```
- **`evaluateQuest(quest, stats) → { progress, target, done }`** is a pure function in `dailyQuests.js`. The UI never computes progress inline; it calls `evaluateQuest`.

Live wiring (the only store changes, additive):

- `recordAnswer(correct, operation)` — **extended signature** (operation optional, defaults to current lesson's operation passed by `LessonEngine`). On every call it bumps `answerCount`, bumps `answerByOperation[operation]`, and maintains an **in-memory run counter** `_currentRunCorrect`: `+1` on correct, reset to `0` on wrong; `bestStreakInSession = max(bestStreakInSession, _currentRunCorrect)`. These updates flow through a new `bumpQuestStats(patch)` store action that writes to the `dailyQuests` row for today.
- `completeLesson(lessonId, accuracy)` — after its existing progress write, if **not practice**, increments `lessonCount` and sets `bestLessonStars = max(bestLessonStars, starsThisLesson)`.
- **"5 in a row" is session-scoped, not cross-session:** the run counter resets to 0 whenever a lesson is entered (`resetLesson`) and on any wrong answer. We persist only `bestStreakInSession` for the day, so reloading mid-day keeps the best run achieved but does not let a kid resume a broken run. (Decision: simpler and harder to game than persisting the live run.)

**Why:** The lesson loop already calls `recordAnswer` and `completeLesson` for every answer/completion; we hang quest accounting off those exact call sites instead of adding event emitters, so coupling stays at "pass one more arg + one more store write."

### 5. Dexie shape + midnight reset

New table, `db.version(2)`:

```js
db.version(2).stores({
  users: '++id, name',
  units: 'id, moduleId, topic, order',
  lessons: 'id, unitId, order',
  progress: 'lessonId, completed',
  streakHistory: 'date',
  dailyQuests: 'date',            // NEW — keyed by "YYYY-MM-DD"
});
```

`ensureTodayQuests()` store action (called on `loadUser` and when the home screen mounts): compute `today = getLocalDateString()`. If `db.dailyQuests.get(today)` exists, use it. Otherwise create a fresh row with `selectDailyQuests(today, ageBand)` IDs and zeroed counters. **Old rows are left in place** (cheap, and useful later for history); we do not delete yesterday's row. Reset is implicit: a new local date → a new key → a new row, so quests "reset at local midnight" for free with no timer.

**Mid-session midnight rollover:** `bumpQuestStats` always re-reads `getLocalDateString()` at write time and writes to *that* date's row, creating it on demand. So if midnight passes mid-lesson, subsequent answers accrue to the new day's quests (correct behavior — the board the kid sees after the lesson is the new day's).

**Why:** Keyed-by-date row + compute-on-read is the same pattern `streakHistory` already uses; no scheduler, no cron, survives offline and clock changes gracefully.

### 6. Reward: bonus heart, with XP fallback — and double-claim prevention

Completing **all three** quests unlocks a **claim** action awarding **+1 heart** (`gainHeart()`), falling back to **+25 XP** (`addXp(25)`) only if the child is already at `MAX_HEARTS`. The claim is **manual** (a button on the board) rather than automatic so the kid gets a satisfying tap and we get a clean single-write claim point.

Double-claim prevention: the `claimed` boolean on the row. `claimQuestReward()` re-reads the row inside the write, refuses if `!allDone` or `row.claimed`, sets `claimed: true`, then grants the reward. Because the guard and the flag set happen in one Dexie write before the reward call, a double tap is a no-op.

**Why:** A heart is the most desirable reward in this app (it gates play), but hearts cap at 10, so XP is the graceful fallback; the persisted `claimed` flag is the simplest idempotency guard and matches the offline single-user model (no race with a server).

// Pure, deterministic daily-quest logic. No Date.now / Math.random.

export const QUEST_CATALOG = Object.freeze([
  { id: 'answer-10-any',   type: 'answers',  metric: 'answerCount',     target: 10, operation: null,             icon: '✏️' },
  { id: 'answer-15-any',   type: 'answers',  metric: 'answerCount',     target: 15, operation: null,             icon: '✏️' },
  { id: 'answer-10-mul',   type: 'answers',  metric: 'answerCount',     target: 10, operation: 'multiplication', icon: '✖️' },
  { id: 'answer-10-add',   type: 'answers',  metric: 'answerCount',     target: 10, operation: 'addition',       icon: '➕' },
  { id: 'streak-5',        type: 'streak',   metric: 'streakInSession', target: 5,  operation: null,             icon: '🔥' },
  { id: 'streak-8',        type: 'streak',   metric: 'streakInSession', target: 8,  operation: null,             icon: '🔥' },
  { id: 'stars-3',         type: 'stars',    metric: 'lessonStars',     target: 3,  operation: null,             icon: '⭐' },
  { id: 'finish-1-lesson', type: 'lessons',  metric: 'lessonCount',     target: 1,  operation: null,             icon: '🏁' },
]);

// Operations a band never practices (mirror of skipUnits.js SKIP_UNITS_BY_BAND).
const SKIPPED_OPERATIONS_BY_BAND = {
  '6-7': [],
  '8-10': [],
  '11-12': ['addition', 'subtraction'],
};

export function dateSeed(dateString) {
  let h = 0x811c9dc5;
  for (let i = 0; i < dateString.length; i++) {
    h ^= dateString.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  return h >>> 0;
}

function mulberry32(seed) {
  let a = seed >>> 0;
  return function next() {
    a |= 0;
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

function seededShuffle(items, rng) {
  const arr = [...items];
  for (let i = arr.length - 1; i > 0; i--) {
    const j = Math.floor(rng() * (i + 1));
    [arr[i], arr[j]] = [arr[j], arr[i]];
  }
  return arr;
}

export function selectDailyQuests(dateString, ageBand) {
  const skippedOps = SKIPPED_OPERATIONS_BY_BAND[ageBand] || [];
  const achievable = QUEST_CATALOG.filter(
    (q) => !q.operation || !skippedOps.includes(q.operation)
  );
  const rng = mulberry32(dateSeed(dateString));
  const shuffled = seededShuffle(achievable, rng);

  const picked = [];
  const usedTypes = new Set();
  // Pass 1: greedily pick distinct types.
  for (const q of shuffled) {
    if (picked.length === 3) break;
    if (!usedTypes.has(q.type)) {
      picked.push(q);
      usedTypes.add(q.type);
    }
  }
  // Pass 2: fill remaining slots with whatever is left (distinct ids).
  for (const q of shuffled) {
    if (picked.length === 3) break;
    if (!picked.includes(q)) picked.push(q);
  }
  return picked;
}

function rawProgress(quest, stats) {
  switch (quest.metric) {
    case 'answerCount':
      return quest.operation
        ? stats.answerByOperation?.[quest.operation] || 0
        : stats.answerCount || 0;
    case 'streakInSession':
      return stats.bestStreakInSession || 0;
    case 'lessonStars':
      return stats.bestLessonStars || 0;
    case 'lessonCount':
      return stats.lessonCount || 0;
    default:
      return 0;
  }
}

export function evaluateQuest(quest, stats) {
  const raw = rawProgress(quest, stats);
  const progress = Math.min(raw, quest.target);
  return { progress, target: quest.target, done: raw >= quest.target };
}

export function allQuestsDone(quests, stats) {
  return quests.length > 0 && quests.every((q) => evaluateQuest(q, stats).done);
}

export function questLabel(quest) {
  switch (quest.metric) {
    case 'answerCount':
      return quest.operation
        ? `Answer ${quest.target} ${quest.operation} questions`
        : `Answer ${quest.target} questions`;
    case 'streakInSession':
      return `Get ${quest.target} in a row correct`;
    case 'lessonStars':
      return `Finish a lesson with ${quest.target} stars`;
    case 'lessonCount':
      return quest.target === 1
        ? 'Finish a lesson'
        : `Finish ${quest.target} lessons`;
    default:
      return 'Daily quest';
  }
}

## Risks / Edge Cases / Out of Scope

**Risks & edge cases handled:**
- **Midnight rollover mid-lesson:** `bumpQuestStats` re-reads `getLocalDateString()` per write and creates the target day's row on demand — answers after midnight accrue to the new day. `recordAnswer` writes are fire-and-forget; the home board reads via `useLiveQuery` so it reflects whichever day is current when it renders.
- **Quest unachievable for a band:** `selectDailyQuests` filters operation-specific quests against `SKIPPED_OPERATIONS_BY_BAND` (kept in sync with `skipUnits.js`). The `11-12` band can never draw an addition/subtraction quest.
- **Run-streak gaming:** "5 in a row" is session-scoped, resets on `resetLesson` and on any wrong answer; only `bestStreakInSession` (the day's best) persists, so closing/reopening can't stitch a broken run together.
- **Double-claim:** the `claimed` flag is flipped in its own Dexie write before the reward is granted; a second `claimQuestReward` returns `alreadyClaimed` and grants nothing.
- **Heart cap:** reward falls back to +25 XP when the child is already at `MAX_HEARTS`, so the claim is never a no-op surprise.
- **`recordAnswer` signature change:** the new `operation` param is optional; any caller passing nothing simply bumps the total counter and skips the per-operation bump. Existing tests that call `recordAnswer(true)` keep working.
- **DB version bump:** `version(1)` is retained for Dexie's upgrade history; the new `dailyQuests` table starts empty, so no migration or backfill is required.

**Out of scope (v1):**
- Quest history / "quests completed this week" view (rows are retained, but no UI reads old days).
- Cross-session or multi-day streak quests; quests are strictly same-day.
- Configurable / per-child quest difficulty, weekend "bonus" quests, or quest-chain rewards.
- Per-operation quests beyond addition/multiplication, and testing operations independently.
- Animations/confetti on claim beyond the existing XP fly-up patterns (can reuse later).
- Pruning old `dailyQuests` rows (storage is negligible; revisit if it ever matters).
