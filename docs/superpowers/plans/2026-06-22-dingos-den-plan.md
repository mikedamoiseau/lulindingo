# Dingo's Den Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Follow the milestone branch/PR workflow in MEMORY.md (one branch per milestone, TDD, PR for review, Slack notify #lulindingo).

**Goal:** Turn the flat `totalXp` number into a reward the child can *spend*. XP doubles as "acorns" — a soft currency the kid spends to unlock and place decor around the existing SVG Dingo mascot (burrow, plants, pond, weather, day/night sky) and optional avatar cosmetics (hats, body colors). The den is rendered as additional SVG layers around the `Mascot` component and rebuilds instantly offline on every load from a new Dexie field.

**User goal (kid POV):** "I earned acorns by doing math. Now I get to spend them to build Dingo a home and dress Dingo up — and it's *mine*, it stays."

**Architecture:** All economy rules live in one pure module `src/utils/denEconomy.js` (balance, affordability, purchase/place reducers) with vitest tests — components stay thin, mirroring the `progression.js` / `placementScoring.js` convention. The decor + cosmetic catalog is a static data file (`src/data/den/catalog.js`) following the `units.js` static-catalog pattern. Persistence adds two fields to the user record via a Dexie `version(2)` bump. The Den is a new route/tab (`/den`). Decor SVG is *generated* from catalog parameters (shape primitive + palette + slot transform), not hand-authored path art per item — same convention as `Mascot.jsx` building shapes from data.

**Tech Stack:** React 19, Zustand, Dexie/IndexedDB, Vitest, CSS Modules.

## KEY DESIGN DECISIONS

Each decision is an opinionated call with a one-line justification.

1. **Currency = a separate "acorns" balance derived from XP, NOT decremented XP.**
   `acornBalance = totalXp - spentAcorns`. `totalXp` and any level/progression signals stay 100% intact; we only ever add to `spentAcorns`. — *Spending must never cannibalize progression; deriving the spendable balance keeps levels truthful while giving the kid something to spend.*

2. **`spentAcorns` is a monotonic counter that only increases; balance is computed, never stored.**
   We persist `spentAcorns` (and the layout), and always recompute `acornBalance` on read. — *A computed balance can never drift out of sync with XP the way a second stored balance would (same lazy-compute philosophy as `heartManager`'s hearts).*

3. **1 XP = 1 acorn, no conversion math.**
   The kid sees one number framed two ways ("XP earned" on Progress, "acorns to spend" in the Den). — *Zero cognitive load for a 6-year-old; no exchange-rate confusion.*

4. **Static catalog file `src/data/den/catalog.js`, shaped like `units.js`, with a `CATALOG_VERSION`.**
   Flat array of items, each `{ id, category, name, cost, slot, render }`. — *Mirrors the existing static-catalog convention; versioning lets us evolve the catalog without breaking saved layouts.*

5. **Five decor categories + two cosmetic categories, each mapped to fixed scene slots.**
   Decor: `burrow`, `plants`, `pond`, `weather`, `sky`. Cosmetics: `hat`, `bodyColor`. — *Fixed slots make the scene a deterministic z-ordered stack — no free-form drag math, which is the right scope for "Medium / for kids".*

6. **Placement model = one chosen item id per slot (a map), not free-form coordinates.**
   `denLayout = { slots: { sky, burrow, pond, plants, weather }, cosmetics: { hat, bodyColor } }`. A slot holds at most one *equipped* item id (or `null`). Ownership (what's been bought) is tracked separately in `owned: string[]`. — *Buy once, then equip/swap freely between owned items; no double-charging, no per-pixel positioning.*

7. **Unlock + buy + place is a single "purchase then auto-equip" flow, fully reversible by re-equipping.**
   Tapping an unowned item the kid can afford buys it (adds to `owned`, increments `spentAcorns`) and equips it into its slot. Tapping an owned item just equips it. Equipping `null` clears the slot (free). — *One tap to get + show the reward; re-equip is free so kids can redecorate endlessly without grinding.*

8. **The Den is a new third tab/route `/den` ("Dingo's Den").**
   Added to `TabBar` and `AppLayout`'s router. — *Discoverable, persistent, sits beside Learn/Progress; doesn't clutter the Learning Path.*

9. **Scene composition: `DenScene` renders a single `<svg>` viewBox with ordered layer groups, the existing `Mascot` SVG nested in the middle.**
   z-order: `sky` (back) → `weather` → `pond` → `burrow` → **Mascot** → `plants` (front) → `hat` (on Mascot) ; `bodyColor` is passed into `Mascot` as a prop override. — *Reuses `Mascot` untouched as the centerpiece; layers are just sibling SVG groups, no compositing tricks.*

10. **Decor art is generated by small parameterized renderers keyed off the catalog, not bespoke path files.**
    Each catalog item's `render` is `{ kind: 'ellipse'|'rect'|'cloud'|'plant'|'sun'|'moon'|'hat-*', palette: [...], variant }`; `denRenderers.js` maps `kind` → React SVG element built from numeric params. — *Matches the convention used by `Mascot.jsx` (shapes from data), keeps the catalog data-only, avoids hand-authored art and keeps the bundle tiny.*

11. **`Mascot.jsx` gains optional props but its default render is byte-for-byte unchanged.**
    New optional props: `bodyColor` (overrides the orange fills) and `hat` (renders an extra group). Defaults reproduce today's output. — *No regression risk for the ~20 existing `Mascot` usages on the Learning Path etc.*

12. **Day/night sky is a manual cosmetic choice, not clock-driven.**
    `sky` slot items include `sky-day`, `sky-sunset`, `sky-night`. — *Deterministic, testable, offline-safe; no surprise theme flips, and the kid controls it.*

## Data Model

### Dexie schema (db.version bump to 2)

`users` keeps `++id, name` indexes (unchanged — extra fields need no index in Dexie). The version bump exists to make the migration explicit and to backfill defaults for the existing single user.

```js
// src/db/database.js
db.version(1).stores({
  users: '++id, name',
  units: 'id, moduleId, topic, order',
  lessons: 'id, unitId, order',
  progress: 'lessonId, completed',
  streakHistory: 'date',
});

// NEW
db.version(2)
  .stores({
    users: '++id, name', // index list unchanged; new fields are index-free
  })
  .upgrade(async (tx) => {
    await tx.table('users').toCollection().modify((u) => {
      if (u.spentAcorns == null) u.spentAcorns = 0;
      if (u.denLayout == null) u.denLayout = createDefaultLayout();
    });
  });
```

Two new user fields:

| Field | Type | Default | Meaning |
|---|---|---|---|
| `spentAcorns` | number | `0` | Monotonic total acorns spent. `balance = totalXp - spentAcorns`. |
| `denLayout` | object | `createDefaultLayout()` | The owned items + equipped slot/cosmetic map. |

`denLayout` shape:

```js
{
  version: 1,            // mirrors CATALOG_VERSION the layout was written against
  owned: ['sky-day'],    // item ids the kid has purchased (free starters allowed)
  slots: {               // one equipped decor item id per slot, or null
    sky: 'sky-day',
    weather: null,
    pond: null,
    burrow: null,
    plants: null,
  },
  cosmetics: {           // one equipped cosmetic id per cosmetic category, or null
    hat: null,
    bodyColor: null,
  },
}
```

`createUser` must also seed `spentAcorns: 0` and `denLayout: createDefaultLayout()` so new users match upgraded users.

**Invariants the tests must lock:**
- `acornBalance` clamps at 0 even if `spentAcorns > totalXp` (defensive — should never happen).
- `purchaseItem` for an unaffordable item returns `ok:false` and identical `spentAcorns`/`layout` (no negative balance, no mutation).
- `purchaseItem` for an already-owned item never increments `spentAcorns`.
- `spentAcorns` after any `purchaseItem` is `>= input spentAcorns`.
- Equipping writes the id into the correct `slots[slot]` (decor) or `cosmetics[category]` (hat/bodyColor) based on the catalog item, never the wrong bucket.
- `equipItem(null, ...)` for a given slot clears it (caller passes a `{ slot }` sentinel or a dedicated `clearSlot(slot, layout)` — implement `clearSlot`).
- `migrateLayout` drops ids absent from the catalog and never throws on an empty/`undefined` layout (returns a default).

## Risks / Edge Cases

- **Balance must never go negative.** `acornBalance` clamps at 0; `purchaseItem` refuses when `cost > balance` and never mutates. Both are unit-tested. The store action no-ops on `ok:false`.
- **Double-spend / rapid taps.** Buy is idempotent: an owned item is never re-charged (`purchaseItem` checks `owned` first). Two fast taps on an unowned affordable item: first buys+equips, second sees it owned and only re-equips for free.
- **Catalog versioning.** Saved `denLayout` may reference ids removed in a later catalog. `migrateLayout` (run on load, after `loadUser`) drops unknown ids, clears slots pointing at them, and re-adds free starters. `CATALOG_VERSION` stamped into the layout signals when migration ran.
- **XP can be spent then "needed" elsewhere.** It can't — `totalXp` is never decremented, so levels/progression read the full earned XP regardless of spend. This is the whole point of decision #1.
- **Mascot regression.** ~20 existing `Mascot` usages must look identical. Locked by a default-render test; new props are optional with today's literals as defaults.
- **Slot/category mismatch.** A catalog item could declare `category:'hat'` but `slot:'pond'`. `catalog.test.js` asserts cosmetics route to `cosmetics[category]` and decor to `slots[slot]`; renderers/equip use the item's own fields, so a bad entry fails a test rather than corrupting a layout.
- **Offline rebuild.** Everything (catalog static, layout in IndexedDB) is local; no network. `DenScene` renders synchronously from the persisted layout on first paint.

## Out of Scope (v1)

- Free-form drag-and-drop placement / per-pixel coordinates (fixed slots only).
- Clock-driven automatic day/night (manual sky choice instead).
- Animated decor, particle effects, sound.
- Trading, gifting, multiplayer, or any backend sync.
- Earning acorns from anything other than XP (no separate quests).
- Selling items back for a refund (`spentAcorns` is monotonic by design).
- Per-module dens (chess etc.) — the layout is math-agnostic but only one den exists for v1.
